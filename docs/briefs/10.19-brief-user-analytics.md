## Objetivo

Medir la actividad del usuario en la app de la manera más eficiente para descubrir:
1. Puntos de apalancamiento (qué acciones generan más valor)
2. Oportunidades de nuevas funciones (qué flujos son lentos o frustrantes)
3. Patrones para automatización (qué hace el usuario repetidamente)

## Principio de diseño: Datos primero, visualización después

No construir dashboards sin datos. La prioridad es instrumentar los eventos correctos en DB y procesarlos después. Overhead < 5ms por evento.

## Esquema de DB propuesto

```sql
CREATE TABLE user_events (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID NOT NULL REFERENCES auth.users(id),
  event_type  TEXT NOT NULL,           -- 'view_change', 'event_drop', etc.
  occurred_at TIMESTAMPTZ DEFAULT now(),
  metadata    JSONB                     -- { from_view: 'week', to_view: 'day' }
);

CREATE INDEX idx_user_events_user_time ON user_events(user_id, occurred_at DESC);
CREATE INDEX idx_user_events_type ON user_events(user_id, event_type, occurred_at DESC);
```

**Sin RLS compleja** — solo `user_id = auth.uid()`.
**Retención sugerida:** 90 días rolling (eliminar automáticamente con pg_cron o trigger).

## Implementación: Analytics Service

```typescript
// lib/analytics/track.ts
export async function track(
  eventType: string,
  metadata?: Record<string, unknown>
): Promise<void> {
  // Fire-and-forget: nunca bloquea la UI
  void fetch('/api/analytics', {
    method: 'POST',
    body: JSON.stringify({ eventType, metadata }),
    headers: { 'Content-Type': 'application/json' },
  }).catch(() => {}) // silencioso en error
}
```

```typescript
// app/api/analytics/route.ts
export async function POST(req: Request) {
  const { eventType, metadata } = await req.json()
  const supabase = createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return new Response(null, { status: 401 })

  await supabase.from('user_events').insert({
    user_id: user.id,
    event_type: eventType,
    metadata,
  })
  return new Response(null, { status: 204 })
}
```

## Queries de insights (futuro)

```sql
-- Vista preferida por hora del día
SELECT
  (metadata->>'to_view') as view,
  EXTRACT(HOUR FROM occurred_at AT TIME ZONE 'America/Guayaquil') as hour,
  COUNT(*) as frequency
FROM user_events
WHERE event_type = 'view_change' AND user_id = $1
GROUP BY view, hour ORDER BY hour;

-- Actividades que se reagendan más (drag frecuente)
SELECT metadata->>'eventTitle' as activity, COUNT(*) as drops
FROM user_events
WHERE event_type = 'event_drop' AND user_id = $1
GROUP BY activity ORDER BY drops DESC LIMIT 10;

-- Ratio plan vs ejecución (tiempo en timer vs tiempo planificado)
SELECT
  DATE(occurred_at AT TIME ZONE 'America/Guayaquil') as day,
  COUNT(*) FILTER (WHERE event_type = 'timer_start') as activities_executed
FROM user_events WHERE user_id = $1
GROUP BY day ORDER BY day DESC;
```

Este sistema es la base para detectar automatizaciones. Una vez con 2–4 semanas de datos, se pueden detectar:
- Actividades que **siempre** se reagendan → candidatos para recurrencia flexible

- Secuencias de actividades que siempre ocurren juntas → plantillas automáticas
